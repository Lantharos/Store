# Data and API

D1 holds who, what and which version; R2 holds files and the signed documents clients read. Everything a client needs is a static, signed file behind the CDN, so installs and updates keep working when the Worker or D1 is having a bad day, and clients don't tell the store what they have installed.

## D1

Better Auth's own tables (`user`, `session`, `account`, `verification`, `passkey`) sit in the same database, defined in the Drizzle schema the way Pult does it. `session.via` says how a session was made: `browser`, `passkey`, or `cli` for the `schelf` command. `approval` holds what the command asked a person to approve: `user_id`, `actions`, `steps` (each in plain words, with its outcome), `secrets` (an upload token made by one, handed to the command once), `passkey`, `status` (pending, running, done, failed, cancelled), `host`, `place`, `expires_at`, `decided_at`. ## R2

One bucket, `schelf-store`, served on `dl.schelf.store` through the api Worker so downloads can be counted. Egress is free either way.

```
apps/<id>/<version>/<platform>/<file>        the artifact, immutable
apps/<id>/<version>/checks/<name>.json       detail of each check
apps/<id>/deltas/<from>-<to>/<platform>.zst
media/<id>/<hash>.<ext>                      icons and screenshots, content-addressed
media/publishers/<id>/<hash>.<ext>           publisher logos, content-addressed
private/verification/<request>/<hash>.<ext>  documents sent for verification, never served
invited/apps/<id>/<version>/<platform>/<file>  the files of releases made on an invite-only channel
invited/index/v1/apps/<id>/<channel>.json    the app's index with that channel's releases in, signed
invited/sabine/<id>/<channel>.json           Sabine's feed for an invite-only channel
index/v1/catalog.json                        every listed app and extension
index/v1/apps/<id>.json                      one app: listing in every locale, releases, artifacts, rollout, what replaced it, and for each extension release the Luft it needs and whether it runs inside Luft
index/v1/mirror/flathub.json                 Flathub apps that pass the quality rules
index/v1/mirror/fedora.json                  Fedora desktop apps that aren't on Flathub
sabine/<id>/<channel>.json                   Sabine update feed, in Sabine's own manifest format
trust/v1/root.pub                            also built into every client
trust/v1/store-keys.json                     current store signing keys, signed by the root
trust/v1/revocations.json                    blocked apps and releases
```

Every JSON file under `index/` and `trust/` is signed: next to `x.json` sits `x.json.sig`, `{"key": "<key id>", "sig": "<base64 Ed25519 signature over the exact bytes of x.json>"}`. A key id is the first 16 hex digits of the SHA-256 of the raw public key. Each signed file carries its `path` in the bucket (`index/v1/catalog.json`, no leading slash), a `serial` and the time it `expires`, inside the signed bytes. The serial is the time of signing in milliseconds, or one more than the last serial of that path if the clock ever reads earlier, so it only grows; it is taken from `store_state` in one statement, and the queue signs one batch at a time, so two writes can't swap. Files the store signs expire 14 days later, and a nightly run signs all of them again, the mirrors included, so nothing lapses while the store is quiet. `store-keys.json` is signed by the root on the owner's computer, so it carries its path and a serial and no expiry: a missed renewal can't take the store down. Sabine feeds carry their signature inside, the way Sabine expects: the manifest is re-encoded in its field order with `rollout` and `key` (the store key id) between `artifacts` and an empty `signature`, and signed. A feed follows the newest approved release of its channel, with that release's rollout percentage. An ended channel's feed carries the release of where the channel points now, under its own channel name, since Sabine refuses a feed for another channel. An app's index lists ended channels in `ended_channels`, each with the open channel it resolves to. The formats, and helpers to sign and verify them, are in `packages/protocol`. Artifacts and media never change after they're written and are cached for a year; index files are cached for 60 seconds with an ETag.

### catalog.json

```json
{
  "version": 1,
  "generated": "2026-11-03T10:00:00Z",
  "apps": [
    {
      "id": "io.github.mira.Cadence",
      "kind": "app",
      "name": "Cadence",
      "summary": "A metronome and practice log for musicians",
      "icon": "https://dl.schelf.store/media/io.github.mira.Cadence/3f9a….png",
      "categories": ["Music"],
      "publisher": { "name": "Mira Halvorsen", "slug": "mira-halvorsen", "verified": true },
      "platforms": {
        "linux-x86_64": { "version": "2.4.0", "format": "sabine", "size": 14820000, "rollout": 25 },
        "windows-x86_64": { "version": "2.4.0", "format": "sabine", "size": 14100000, "rollout": 25 }
      },
      "access": "limited",
      "updated": "2026-10-28T12:00:00Z",
      "installs_30d": 2316
    }
  ]
}
```

`publisher.verified` is the publisher's checkmark, given by a person after [verification](review.md#verification); proving a namespace alone doesn't earn it. Platforms are `linux-x86_64`, `linux-aarch64`, `windows-x86_64`, `windows-aarch64`, `macos-aarch64`, and `luft` for extensions without native code. `access` is `full` or `limited`; the full permission list is in the app's own file, where an extension's release carries `extension`: its `permissions` from the extension API and whether it has a `helper`. Mirror catalogs use the same entry shape (their `publisher` is the upstream developer, `verified` as Flathub says) with `"origin": "flathub"` and a `flathub` ref, or `"origin": "fedora"` and a `package` name, instead of `platforms`.

An app's own file carries `"replaced_by": {"id": "…", "note": "…"}` once another app takes its place. The Schelf app then installs the replacement for everyone who has the old one and removes the old one. It also carries `"privacy": {"telemetry", "ads", "ai"}` when the developer declared it.

## Hosting

Besides the R2 keys above, `dl.schelf.store` answers for every published project at `/<publisher>/<project>`, where the first segment isn't one of the R2 roots (`apps`, `index`, `trust`, `sabine`, `media`, `private`). An optional `@<channel>` segment follows the project; without it, stable.

| Path                                          | Answer                                                                                                                                          |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `latest`                                      | 302 to the visitor's file (user agent and client hints), or to the project page                                                                 |
| `latest/<platform or os>[/<kind>]`            | 302 to the newest file for it, falling back from `macos-aarch64` to `macos-universal`, from `windows-aarch64` to `windows-x86_64`, and to `any` |
| `latest/<part>[/<platform>[/<kind>]]`         | The same for a named part; parts can't take a system's name                                                                                     |
| `v/<version>[/<platform>[/<kind>]]`           | The release as JSON, or 302 to its file                                                                                                         |
| `latest/SHA256SUMS`, `v/<version>/SHA256SUMS` | Checksums, as `sha256sum` writes them                                                                                                           |
| `latest.json`                                 | The newest release and, per platform, the file the link serves                                                                                  |
| `tauri.json`                                  | Tauri's updater format, or 204 with nothing to offer                                                                                            |
| `<channel>[-mac                               | -linux                                                                                                                                          | -linux-arm64].yml` | electron-updater's format; `latest*.yml` is stable |
| `/embed.js`                                   | The download button script                                                                                                                      |

Links resolve against the newest 20 shipped, unblocked releases of the channel, read from D1 and kept in the colo's cache for 60 seconds. An ended channel's links resolve against where it points now, then the channels on the way there. Its Electron and Tauri feeds take the highest version among all of them, because a feed can't see the version asking and electron-updater accepts a lower one from a channel it's set to. Redirects are cached for 60 seconds, except when a rolling-out release was picked by the request's draw. The redirect target is the immutable artifact URL, which counts the download.

## Invite-only channels

Everything under `invited/` is served only to a request that may have it: a link signed by the Worker (`?expires=&access=`, an HMAC of the key and expiry, used for redirects, the dashboard, the page, Pult and the checks workflow), a download token for the channel (`Authorization: Bearer schelfdl_…`), or a Better Auth session (cookie on schelf.store, bearer on dl.schelf.store) of a publisher member or of a person whose verified email is invited. A file stays under `invited/` for good; it's served to anyone once a release on an open channel uses it, which is how promoting it makes it public. Links under `/@<channel>/` of an invite-only channel need the same token or session, answer `no-store`, and redirect to signed file addresses. The public index and Sabine feeds leave invite-only channels out; each has its own signed index and feed under `invited/`, which the Schelf app reads with the person's session. A channel can only become invite-only before its first release, so nothing on it was ever public.

## Counting without tracking

- Every artifact download goes through the Worker, which writes one Analytics Engine data point: app, version, platform, and `install` or `update` from the `reason` query parameter Sabine and the Schelf app set. No IP address, user agent, device id or cookie is written anywhere.
- Only requests starting at byte 0 count, so resumed downloads count once.
- A nightly job sums the day into `count_daily`. The site shows installs over the last 30 days and all time; the dashboard shows the same by version and platform.
- Clients never send their list of installed apps.

### Dashboard

Signed in with Better Auth, under `/dev`: `account` (the person, their publishers with their role in each, and invitations waiting for them), `invites/:id/accept` and `decline`, `publishers` (create a personal publisher or an organisation, accepting the agreement), and per publisher `publishers/:id` (profile, `logo`), `members` (roles, removing and leaving, `:user/transfer`), `invites`, `namespaces` (claim, `:prefix/verify`), `apps` (list, add) and `verification` (the request, `check`, `contact/code` and `contact/confirm`, `github`, `documents`, `submit`, `reply`). Per publisher also `apps/projects` (make an unlisted project). App routes need no publisher, and take the app id or `publisher/project`: `apps/:id` (settings, links, channels, moves and the files to commit), `apps/:id/hosting` (address, indexing, links following rollouts), `apps/:id/listing-request`, `apps/:id/switch` (start or undo a move to a new framework), `apps/:id/channels/:channel` (and its `end` and `reopen`), `apps/:id/uploads` (start a manual upload; the files then go up through the publishing calls), `apps/:id/releases/:release/promote`, `apps/:id/listing/:locale` and `apps/:id/meta` (refused for fields its applied files set, which settings name in `config`), `apps/:id/icon`, `apps/:id/screenshots`, `apps/:id/trusted-publishers`, `apps/:id/tokens`, `apps/:id/releases` (status, checks timeline, `rollout`), `apps/:id/stats`. `requests` (ask for approval), `requests/:id` (its state), `requests/:id/approve` (browser sessions only) and `requests/:id/cancel`. The `schelf` command signs in with Better Auth's device authorization (`/api/auth/device/code`, then `/api/auth/device/token`, client id `schelf-cli`); the person approves the code on `https://schelf.store/device`, and the command sends the session token as a bearer token. Every call checks the person's role in the publisher: developers change releases, rollouts and listings; admins also apps, namespaces, trusted publishers, tokens, members and the public page; owners also other owners, the agreement and verification.


### Webhooks in
