# Data and API

D1 holds who, what and which version; R2 holds files and the signed documents clients read. Everything a client needs is a static, signed file behind the CDN, so installs and updates keep working when the Worker or D1 is having a bad day, and clients don't tell the store what they have installed.

## D1

## R2

One bucket, `schelf-store`, served on `dl.schelf.store` through the api Worker so downloads can be counted. Egress is free either way.

```
apps/<id>/<version>/<platform>/<file>        the artifact, immutable
apps/<id>/<version>/checks/<name>.json       detail of each check
apps/<id>/deltas/<from>-<to>/<platform>.zst
media/<id>/<hash>.<ext>                      icons and screenshots, content-addressed
media/publishers/<id>/<hash>.<ext>           publisher logos, content-addressed
private/verification/<request>/<hash>.<ext>  documents sent for verification, never served
index/v1/catalog.json                        every listed app and extension
index/v1/apps/<id>.json                      one app: listing in every locale, releases, artifacts, rollout
index/v1/mirror/flathub.json                 Flathub apps that pass the quality rules
index/v1/mirror/fedora.json                  Fedora desktop apps that aren't on Flathub
sabine/<id>/<channel>.json                   Sabine update feed, in Sabine's own manifest format
trust/v1/root.pub                            also built into every client
trust/v1/store-keys.json                     current store signing keys, signed by the root
trust/v1/revocations.json                    blocked apps and releases, with a serial
```

Every JSON file under `index/` and `trust/` is signed: next to `x.json` sits `x.json.sig`, `{"key": "<key id>", "sig": "<base64 Ed25519 signature over the exact bytes of x.json>"}`. A key id is the first 16 hex digits of the SHA-256 of the raw public key. Sabine feeds carry their signature inside, the way Sabine expects: the manifest is re-encoded in its field order with `rollout` and `key` (the store key id) between `artifacts` and an empty `signature`, and signed. A feed follows the newest approved release of its channel, with that release's rollout percentage. The formats, and helpers to sign and verify them, are in `packages/protocol`. Artifacts and media never change after they're written and are cached for a year; index files are cached for 60 seconds with an ETag.

### catalog.json

```json
{
  "version": 1,
  "generated": "2026-11-03T10:00:00Z",
  "apps": [
    {
      "id": "io.github.mira.Cadence",
      "kind": "app",
      "name": "Cadence",
      "summary": "A metronome and practice log for musicians",
      "icon": "https://dl.schelf.store/media/io.github.mira.Cadence/3f9a….png",
      "categories": ["Music"],
      "publisher": { "name": "Mira Halvorsen", "slug": "mira-halvorsen", "verified": true },
      "platforms": {
        "linux-x86_64": { "version": "2.4.0", "format": "sabine", "size": 14820000, "rollout": 25 },
        "windows-x86_64": { "version": "2.4.0", "format": "sabine", "size": 14100000, "rollout": 25 }
      },
      "access": "limited",
      "updated": "2026-10-28T12:00:00Z",
      "installs_30d": 2316
    }
  ]
}
```

`publisher.verified` is the publisher's checkmark, given by a person after [verification](review.md#verification); proving a namespace alone doesn't earn it. Platforms are `linux-x86_64`, `linux-aarch64`, `windows-x86_64`, `windows-aarch64`, `macos-aarch64`, and `luft` for extensions without native code. `access` is `full` or `limited`; the full permission list is in the app's own file, where an extension's release carries `extension`: its `permissions` from the extension API and whether it has a `helper`. Mirror catalogs use the same entry shape (their `publisher` is the upstream developer, `verified` as Flathub says) with `"origin": "flathub"` and a `flathub` ref, or `"origin": "fedora"` and a `package` name, instead of `platforms`.

## Hosting

Besides the R2 keys above, `dl.schelf.store` answers for every published project at `/<publisher>/<project>`, where the first segment isn't one of the R2 roots (`apps`, `index`, `trust`, `sabine`, `media`, `private`). An optional `@<channel>` segment follows the project; without it, stable.

| Path | Answer |
| --- | --- |
| `latest` | 302 to the visitor's file (user agent and client hints), or to the project page |
| `latest/<platform or os>[/<kind>]` | 302 to the newest file for it, falling back from `macos-aarch64` to `macos-universal`, from `windows-aarch64` to `windows-x86_64`, and to `any` |
| `v/<version>[/<platform>[/<kind>]]` | The release as JSON, or 302 to its file |
| `latest/SHA256SUMS`, `v/<version>/SHA256SUMS` | Checksums, as `sha256sum` writes them |
| `latest.json` | The newest release and, per platform, the file the link serves |
| `tauri.json` | Tauri's updater format, or 204 with nothing to offer |
| `<channel>[-mac|-linux|-linux-arm64].yml` | electron-updater's format; `latest*.yml` is stable |
| `/embed.js` | The download button script |

Links resolve against the newest 20 shipped, unblocked releases of the channel, read from D1 and kept in the colo's cache for 60 seconds. Redirects are cached for 60 seconds, except when a rolling-out release was picked by the request's draw. The redirect target is the immutable artifact URL, which counts the download.

## Counting without tracking

- Every artifact download goes through the Worker, which writes one Analytics Engine data point: app, version, platform, and `install` or `update` from the `reason` query parameter Sabine and the Schelf app set. No IP address, user agent, device id or cookie is written anywhere.
- Only requests starting at byte 0 count, so resumed downloads count once.
- A nightly job sums the day into `count_daily`. The site shows installs over the last 30 days and all time; the dashboard shows the same by version and platform.
- Clients never send their list of installed apps.

## API

All under `https://schelf.store/api/v1`.

### Public

| Call                                     | Purpose                                                                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /search?q=&locale=&platform=&kind=` | Ranked search over store apps and the mirror: names that start with the query first, then close matches, so misspellings still find things. |
| `GET /featured?locale=&platform=`        | Home page sections.                                                                                                                         |
| `GET /apps/:id`                          | One app for the storefront, with install counts and its project summary (address, listed, indexed, page, latest link).                      |
| `GET /projects/:publisher/:project`      | The same, by the project's address.                                                                                                         |
| `GET /publishers/:slug`                  | A publisher's page: name, description, website, logo, whether it's verified, and its listed apps and extensions.                            |
| `GET /mirror/:id?origin=`                | One Flathub or Fedora app from the mirror; Flathub's when both have it.                                                                     |
| `POST /reports`                          | Report an app (DSA notice form).                                                                                                            |

### Dashboard

Signed in with Better Auth, under `/dev`: `account` (the person, their publishers with their role in each, and invitations waiting for them), `invites/:id/accept` and `decline`, `publishers` (create a personal publisher or an organisation, accepting the agreement), and per publisher `publishers/:id` (profile, `logo`), `members` (roles, removing and leaving, `:user/transfer`), `invites`, `namespaces` (claim, `:prefix/verify`), `apps` (list, add) and `verification` (the request, `check`, `contact/code` and `contact/confirm`, `github`, `documents`, `submit`, `reply`). Per publisher also `apps/projects` (make an unlisted project). App routes need no publisher, and take the app id or `publisher/project`: `apps/:id` (settings, links, channels, moves and the files to commit), `apps/:id/hosting` (address, indexing, links following rollouts), `apps/:id/listing-request`, `apps/:id/switch` (start or undo a move to a new framework), `apps/:id/channels/:channel`, `apps/:id/uploads` (start a manual upload; the files then go up through the publishing calls), `apps/:id/releases/:release/promote`, `apps/:id/listing/:locale` and `apps/:id/meta` (each takes a `source`: `appstream` or `sabine` when the schelf command fills them in, `dashboard` otherwise; settings return `listing_sources` and `meta_sources`), `apps/:id/icon`, `apps/:id/screenshots`, `apps/:id/trusted-publishers`, `apps/:id/tokens`, `apps/:id/releases` (status, checks timeline, `rollout`), `apps/:id/stats`. The `schelf` command signs in with Better Auth's device authorization (`/api/auth/device/code`, then `/api/auth/device/token`, client id `schelf-cli`); the person approves the code on `https://schelf.store/device`, and the command sends the session token as a bearer token. Every call checks the person's role in the publisher: developers change releases, rollouts and listings; admins also apps, namespaces, trusted publishers, tokens, members and the public page; owners also other owners, the agreement and verification.
